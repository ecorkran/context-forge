[x] **(910) Centralize NormalizedStatus Value References** — The `NormalizedStatus` values (`complete`, `in-progress`, `not-started`, `deprecated`) exist only as a TypeScript type union, so every comparison and assignment re-types the bare literal — ~50 sites across `ConsistencyChecker.ts` (~40), `ProjectModelBuilder.ts`, `WorkflowNavigator.ts`, `taskFileParser.ts`, `slicePlanParser.ts`, and `statusNormalizer.ts`. Introduce a `STATUS` `as const` object in `introspection/types.ts` with the type derived from it (`type NormalizedStatus = (typeof STATUS)[keyof typeof STATUS]`, keeping the union byte-identical), then sweep all literal sites to reference `STATUS.Complete` etc. Pure mechanical refactor, no behavior change — the existing test suite is the regression guard. Note: slice 241 introduces the `STATUS` constant for its own new code; this slice completes the sweep of pre-existing sites. Dependencies: 241 (constant already defined). Risk: Medium. Effort: 3/5

[x] **(911) Fix Slice-Status Derivation for Partial-Completion Slices** [design: `user/slices/911-slice.workflow-status-derivation.md`] — `workflow_status`/`workflow_check` (and `cf status`/`cf next`/`cf list slices`) collapse a genuinely in-progress slice (task file frontmatter `in_progress`, partial task completion, or even 100% task completion with a still-unchecked plan entry) into the same `not-started` bucket as a slice that's never been touched. Reproduced directly against slice 242 post-completion: `cf status` correctly reported `complete` (26/26 tasks), but `cf next`/`cf list slices` both called it "not started" and recommended advancing into it as the next unstarted slice. Fixes GitHub issue #56. Root cause (per the issue): whatever maps frontmatter status + task-completion ratio to a slice-plan-entry's derived `status` only distinguishes fully-checked-`complete` from a single not-started fallback, with no `in-progress`-with-partial-completion branch. Also add a `workflow_check` rule to catch this class of mismatch (task file `in_progress` with partial/full completion vs. a derived `not-started` plan-entry status), mirroring the existing `plan-vs-frontmatter`/`frontmatter-vs-computed` rules. Additionally resolves GitHub issue #57 (docs-only slices gated for a `code` review they cannot produce): a set-once slice-design frontmatter declaration read by `evaluateReviewGate()` at the pre-advance boundary, registered as an optional field in the `slice-design` frontmatter schema. #57 rides along because it shares the derivation slice's on-disk-signal machinery and its verification fixtures (slice 243). Dependencies: 241 (`STATUS` const), 242 (`evaluateReviewGate` extraction) — both complete on `main`. Risk: Medium (touches shared status-derivation logic used by multiple commands). Effort: 3/5

(b) `ConsistencyChecker.ruleReviewGate()` hardcodes the `preAdvance` boundary only — `cf check`/`workflow_check` never flags a missing `arch`, `slice`, or `tasks` review, only `code`; needs sibling checks (or an extended rule) covering all four boundaries via the existing `evaluateReviewGate()`. 13. [x] **(913) Fix Phantom Low-Index Review-Gate Findings, 909's Missing Slice-Design, and List-Command Plan Targeting** — Three related `cf check`/`cf list` fixes found while dogfooding review gating (initiative 240) on this repo, post-243:
    (a) **Phantom "Slice 1"–"Slice 12" review-gate findings.** `ConsistencyChecker.discoverAllSlicePlans()` (`ConsistencyChecker.ts:1169–1180`) globs *every* `*-slices.*.md` file in `project-documents/user/architecture/` — not just the project's active plan — and `checkAll()` merges every discovered plan's entries into one `index`-keyed map. `slicePlanParser.ts`'s unindexed-entry fallback (`PLAN_UNINDEXED_RE`, used when a list item has no bolded `(NNN)`) assigns a per-file sequential counter (1, 2, 3…) as that entry's `index` — a reasonable fallback in isolation, but it collides with real project-wide slice indices once merged globally. Legacy plan `140-slices.context-forge-restructure.md` (fully complete, pre-dates the `(NNN)` convention) is the actual source: its 12 unindexed entries surface as bogus `Slice 1`–`Slice 12` review-gate findings. Fix: either (i) scope `discoverAllSlicePlans()`/`checkAll()`'s review-gate evaluation to plans using the indexed format only (skip unindexed-fallback entries for gate purposes), or (ii) exclude historical/completed legacy plans from cross-plan gate aggregation entirely — decide the correct approach at design time; a real regression test using plan 140's actual unindexed format is required either way.
    (b) **Slice 909 has no slice-design file, so `--set-review-none` can't help it.** 909 ("Configurable Branch Root Prefix") is checked `[x]` in the 900 slice plan, but there is no `909-slice.*.md` for `cf check --set-review-none 909` to write into (confirmed: `detectDocuments` finds nothing, command correctly refuses). This is **not** a case of the work happening outside this repo — the CF-side implementation (the `git.branch_root` config key, its validator, and 45 lines of coverage in `ConfigManager.test.ts`) shipped here in commit `713d0c0` ("feat(core): add git.branch_root config key", 20260628). Only the companion branch-naming convention (which reads the key) lives upstream in the ai-project-guide submodule — the commit message itself records the decision explicitly: "Tracked as a (909) maintenance note rather than a standalone initiative," i.e. the design/task artifact trail was deliberately skipped in favor of an inline plan note. Fix: write a minimal retroactive slice-design for 909 (`909-slice.configurable-branch-root-prefix.md`) documenting what actually shipped, citing `713d0c0` as the implementation commit, so it has a normal artifact to declare `codeReview: none` on (or to receive a real code review against, if one is warranted retroactively) — rather than inventing a new exemption mechanism for something that is, in fact, ordinary shipped CF code.
    (c) **`cf list slices`/`cf list tasks` can't target a non-active plan/initiative.** Both commands only ever read whatever `fileSlicePlan`/current project state points to (`packages/cli/src/commands/list.ts:61–82`, no positional index argument). Inspecting another initiative's slices/tasks today requires `cf status` → `cf set arch <n>` → `cf list slices` → `cf set arch <back>`, a disruptive four-step round-trip that mutates and restores project state just to look. Add an optional `[archIndex]` positional argument to both `cf list slices` and `cf list tasks` that reads the target plan/task files directly without touching the project's configured `arch`/`slicePlan` state.
    Dependencies: 240/241/242/911/912 (review-gate system this dogfoods against). Risk: Low–Medium (item (a) touches shared cross-plan aggregation logic; (b) may be policy-only; (c) is additive CLI surface). Effort: 3/5

[x] **(914) Rename git.branch_root to git.integration_branch** — `git.branch_root` (909) turned out to be the wrong shape: a pure branch-name string prefix that never changed fork-from/merge-to targets (always `main`). Real usage (GitHub-Flow/GitFlow-style long-lived integration branches, e.g. `dev/erik`) needs the config value to also change git topology: when set, work branches fork from and merge into the integration branch, never `main` (merging the integration branch to `main` is PM-only, outside automation scope). This slice is the CF-side half only: rename the config key `git.branch_root` → `git.integration_branch` in `packages/core/src/config/ConfigKeys.ts` (same validation, updated description), update `ConfigManager.test.ts` accordingly, and sweep any other in-repo references to the old key name. Clean rename, no deprecated alias. The companion branch-naming/fork/merge rule change (including elimination of the separate `{index}-planning.{name}` branch type) lives upstream in the `ai-project-guide` submodule and is out of scope here. Dependencies: none. Risk: Low. Effort: 1/5
15. [x] **(915) Config Key Scope Classification (Shared vs. Personal)** — `cf config set --project` writes every key into one `.context-forge.toml` at the repo root, with no distinction between team-wide policy (`workflow.*`, `guide.*` — should be committed so all developers share the same conventions) and per-developer settings (`git.integration_branch` — must never be committed; each developer/worktree needs their own). Today this is an all-or-nothing gitignore decision left entirely to the user, and the two classes of key get silently conflated in the same file. Add a `scope: 'shared' | 'personal'` classification to each entry in the `CONFIG_KEYS` registry (`packages/core/src/config/ConfigKeys.ts`), and route project-scoped reads/writes through `ConfigManager`/`configPaths.ts` to the appropriate file per key's scope — reusing the existing user-vs-project two-file-precedence merge pattern rather than inventing a new one. `cf init` should ensure the personal-scope file is covered by `.gitignore` (minimal addition — the one line needed for this feature, not a full gitignore overhaul, which is tracked separately as a Future Work item below). Needs a defined migration/compat story for projects that already committed personal keys (e.g. `git.integration_branch`) into an existing shared `.context-forge.toml` before this classification existed. Dependencies: none. Risk: Low–Medium (new file-routing logic, migration/compat story, touches `packages/mcp-server` config tools too). Effort: 3/5
16. [x] **(916) Guide Update Branch Guard** — `cf guide update` (`GuideManager.update()`, `packages/core/src/guides/GuideManager.ts`) autonomously commits directly to whatever branch is currently checked out — confirmed via `SubmoduleStrategy.update()` and `CloneStrategy.update()`, both of which run `git add`/`git commit` in the host project's `projectPath` with zero branch-awareness anywhere in the guide-update path. When `git.integration_branch` is set specifically to prevent direct changes to `main` (work branches fork from/merge into it instead), guide update bypasses that guardrail entirely — it will happily commit straight to `main` regardless of the configured policy. Add a branch guard evaluated before any commit: resolve `trunk` = `git.integration_branch` if set, else `main`. (a) current branch == `trunk` → proceed silently (unchanged behavior). (b) current branch == `main` AND `trunk` != `main` (i.e. integration branch is configured and the user is on `main`) → **block** with an explicit error naming the configured integration branch. (c) otherwise, run `git merge-base --is-ancestor <trunk> HEAD` via the existing generic `gitExec()` helper (`packages/core/src/guides/gitExec.ts:14-28`, already used by all strategies — no new git-invocation plumbing needed): exit 0 (current branch descends from trunk, e.g. a feature/test branch cut from the integration branch, or from `main` when no integration branch is set) → warn, proceed with confirmation; exit 1 (branch shares no resolvable ancestry with trunk) → warn more strongly, still confirmation-gated rather than a hard block. This applies identically whether or not `git.integration_branch` is set — the "not on trunk" warn-and-confirm case is the same question in both modes, only the value of `trunk` differs. `TarballStrategy` (manual strategy, no git commit) is unaffected since it does no git plumbing to guard. Dependencies: 914 (config key is `git.integration_branch`, not the old `git.branch_root`). Risk: Low (additive guard, no change to existing on-trunk behavior). Effort: 2/5
