[x] **(905) Frontmatter Schema Validation** — Define required and optional YAML frontmatter fields per `docType` (e.g., `slice-plan` requires `status`, `docType`, `parent`; `slice` requires `status`, `docType`, `parent`, `slice`; `tasks` requires `status`, `slice`, `project`). Implement a schema registry in `packages/core` that maps `docType` values to field requirements with types and allowed values. Extend `ConsistencyChecker` to validate all project documents against their schema — detecting missing required fields, unknown fields, and invalid values. Currently Rule 9 hard-codes a check for missing `status` on slice plans; this would generalize that pattern to all document types and all required fields. The schema registry should be data-driven (e.g., a config file or typed constant) so adding new document types or fields doesn't require rule code changes. Dependencies: none. Risk: Low. Effort: 3/5

[x] **(907) CLI Short-Form Options & Option Centralization** — Add standard short-form flags (`-j`/`--json`, `-p`/`--project`, `-y`/`--yes`, `-f`/`--fix`, `-a`/`--all`, `-r`/`--raw`) and centralize the ~70 inline `.option()` registrations into shared helpers. Create a shared `options.ts` module with composable helpers (e.g., `withJsonOption`, `withProjectOption`) so adding or changing a common option is a one-line edit instead of 16. Dependencies: none. Risk: Low. Effort: 2/5

Dependencies: none. Risk: Low. Effort: 2/5
9. [x] **(909) Configurable Branch Root Prefix** — Optional per-project prefix prepended to work branch names (e.g. `myroot/910-slice.foo`), so branches can live under a chosen root without affecting document/artifact resolution. CF side: added `git.branch_root` config key (project-scoped, default empty = no prefix) with validation rejecting absolute, `..`-escaping, and trailing-slash values (`packages/core/src/config/ConfigKeys.ts` + tests). Convention side: the branch-naming rule in `ai-project-guide/project-guides/rules/git.md` instructs agents to read `cf config get git.branch_root` and prefix when non-empty — this change lives in the **ai-project-guide submodule (upstream)**, not in this repo; it lands here when the submodule pointer is next updated. Originally scoped as initiative 910 (configurable root directory) but collapsed to this note once the real need turned out to be a branch-name prefix, not a filesystem relocation. Dependencies: upstream `git.md` guide change. Risk: Low. Effort: 1/5
10. [ ] **(910) Centralize NormalizedStatus Value References** — The `NormalizedStatus` values (`complete`, `in-progress`, `not-started`, `deprecated`) exist only as a TypeScript type union, so every comparison and assignment re-types the bare literal — ~50 sites across `ConsistencyChecker.ts` (~40), `ProjectModelBuilder.ts`, `WorkflowNavigator.ts`, `taskFileParser.ts`, `slicePlanParser.ts`, and `statusNormalizer.ts`. This violates the "define comparison values once, reference everywhere" rule: changing a status string requires editing dozens of places. Introduce a `STATUS` `as const` object in `introspection/types.ts` with the type derived from it (`type NormalizedStatus = (typeof STATUS)[keyof typeof STATUS]`, keeping the union byte-identical), then sweep all literal sites to reference `STATUS.Complete` etc. Pure mechanical refactor, no behavior change — the existing test suite is the regression guard. Note: slice 241 introduces the `STATUS` constant for its own new code; this slice completes the sweep of pre-existing sites. Dependencies: 241 (constant already defined). Risk: Medium. Effort: 3/5
11. [x] **(911) Fix Slice-Status Derivation for Partial-Completion Slices** [design: `user/slices/911-slice.workflow-status-derivation.md`] — `workflow_status`/`workflow_check` (and `cf status`/`cf next`/`cf list slices`) collapse a genuinely in-progress slice (task file frontmatter `in_progress`, partial task completion, or even 100% task completion with a still-unchecked plan entry) into the same `not-started` bucket as a slice that's never been touched. Reproduced directly against slice 242 post-completion: `cf status` correctly reported `complete` (26/26 tasks), but `cf next`/`cf list slices` both called it "not started" and recommended advancing into it as the next unstarted slice. Fixes GitHub issue #56. Root cause (per the issue): whatever maps frontmatter status + task-completion ratio to a slice-plan-entry's derived `status` only distinguishes fully-checked-`complete` from a single not-started fallback, with no `in-progress`-with-partial-completion branch. Also add a `workflow_check` rule to catch this class of mismatch (task file `in_progress` with partial/full completion vs. a derived `not-started` plan-entry status), mirroring the existing `plan-vs-frontmatter`/`frontmatter-vs-computed` rules. Additionally resolves GitHub issue #57 (docs-only slices gated for a `code` review they cannot produce): a set-once slice-design frontmatter declaration read by `evaluateReviewGate()` at the pre-advance boundary, registered as an optional field in the `slice-design` frontmatter schema. #57 rides along because it shares the derivation slice's on-disk-signal machinery and its verification fixtures (slice 243). Dependencies: 241 (`STATUS` const), 242 (`evaluateReviewGate` extraction) — both complete on `main`. Risk: Medium (touches shared status-derivation logic used by multiple commands). Effort: 3/5
12. [x] **(912) Fix cf next Stale-Phase Remediation and Review-Gate Coverage Gaps** [design: `user/slices/912-slice.fix-cf-next-and-review-gate-coverage.md`] — Fixes GitHub issue #58: when `arch` is correctly set but its file doesn't exist yet (a normal transition between initiatives) and `phase` is stale (left over from the prior initiative), `cf next` suggests `cf set arch <index>` — a no-op, since arch is already correct — instead of the actually-correct remediation, `cf set phase <architecture-phase>`. The rationale text is correct; only the suggested `Run:` command is wrong. Also fixes GitHub issue #59 (found while dogfooding slice 911's review-gate work on this repo): (a) the `preSlicePlan`/arch review gate in `WorkflowNavigator.getNext()` only evaluates inside the `no-active-slice` guard when no slice plan exists yet (`archFileExists && status.slicePlan === null`) — once a slice plan is created, the arch review requirement silently stops being checked forever, even if the architecture was never reviewed; needs to evaluate per-arch-index independently of slice-plan existence, mirroring how the other three boundaries key off the active slice regardless of what else exists. (b) `ConsistencyChecker.ruleReviewGate()` hardcodes the `preAdvance` boundary only — `cf check`/`workflow_check` never flags a missing `arch`, `slice`, or `tasks` review, only `code`; needs sibling checks (or an extended rule) covering all four boundaries via the existing `evaluateReviewGate()`. The 911 effective-date grandfather cutoff (`workflow.review_gate_effective_date`) is already centralized in `evaluateReviewGate()`, so widening `cf check`'s coverage here should not need any additional cutoff plumbing — confirm this holds during design. Dependencies: 240/241/242 (review gate system), 911 (`evaluateReviewGate`, effective-date cutoff). Risk: Medium (touches the same shared gate-evaluation path as 911). Effort: 3/5
13. [ ] **(913) Fix Phantom Low-Index Review-Gate Findings, 909's Missing Slice-Design, and List-Command Plan Targeting** — Three related `cf check`/`cf list` fixes found while dogfooding review gating (initiative 240) on this repo, post-243:
    (a) **Phantom "Slice 1"–"Slice 12" review-gate findings.** `ConsistencyChecker.discoverAllSlicePlans()` (`ConsistencyChecker.ts:1169–1180`) globs *every* `*-slices.*.md` file in `project-documents/user/architecture/` — not just the project's active plan — and `checkAll()` merges every discovered plan's entries into one `index`-keyed map. `slicePlanParser.ts`'s unindexed-entry fallback (`PLAN_UNINDEXED_RE`, used when a list item has no bolded `(NNN)`) assigns a per-file sequential counter (1, 2, 3…) as that entry's `index` — a reasonable fallback in isolation, but it collides with real project-wide slice indices once merged globally. Legacy plan `140-slices.context-forge-restructure.md` (fully complete, pre-dates the `(NNN)` convention) is the actual source: its 12 unindexed entries surface as bogus `Slice 1`–`Slice 12` review-gate findings. Fix: either (i) scope `discoverAllSlicePlans()`/`checkAll()`'s review-gate evaluation to plans using the indexed format only (skip unindexed-fallback entries for gate purposes), or (ii) exclude historical/completed legacy plans from cross-plan gate aggregation entirely — decide the correct approach at design time; a real regression test using plan 140's actual unindexed format is required either way.
    (b) **Slice 909 has no slice-design file, so `--set-review-none` can't help it.** 909 ("Configurable Branch Root Prefix") is checked `[x]` in the 900 slice plan, but there is no `909-slice.*.md` for `cf check --set-review-none 909` to write into (confirmed: `detectDocuments` finds nothing, command correctly refuses). This is **not** a case of the work happening outside this repo — the CF-side implementation (the `git.branch_root` config key, its validator, and 45 lines of coverage in `ConfigManager.test.ts`) shipped here in commit `713d0c0` ("feat(core): add git.branch_root config key", 20260628). Only the companion branch-naming convention (which reads the key) lives upstream in the ai-project-guide submodule — the commit message itself records the decision explicitly: "Tracked as a (909) maintenance note rather than a standalone initiative," i.e. the design/task artifact trail was deliberately skipped in favor of an inline plan note. Fix: write a minimal retroactive slice-design for 909 (`909-slice.configurable-branch-root-prefix.md`) documenting what actually shipped, citing `713d0c0` as the implementation commit, so it has a normal artifact to declare `codeReview: none` on (or to receive a real code review against, if one is warranted retroactively) — rather than inventing a new exemption mechanism for something that is, in fact, ordinary shipped CF code.
    (c) **`cf list slices`/`cf list tasks` can't target a non-active plan/initiative.** Both commands only ever read whatever `fileSlicePlan`/current project state points to (`packages/cli/src/commands/list.ts:61–82`, no positional index argument). Inspecting another initiative's slices/tasks today requires `cf status` → `cf set arch <n>` → `cf list slices` → `cf set arch <back>`, a disruptive four-step round-trip that mutates and restores project state just to look. Add an optional `[archIndex]` positional argument to both `cf list slices` and `cf list tasks` that reads the target plan/task files directly without touching the project's configured `arch`/`slicePlan` state.
    Dependencies: 240/241/242/911/912 (review-gate system this dogfoods against). Risk: Low–Medium (item (a) touches shared cross-plan aggregation logic; (b) may be policy-only; (c) is additive CLI surface). Effort: 3/5
